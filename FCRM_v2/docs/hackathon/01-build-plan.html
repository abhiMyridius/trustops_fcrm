01bUse-case scope · what the workbench covers in this build

Financial-crime risk assessment of changes at a US bank, before go-live. Not fraud, not credit, not transaction-monitoring operations. Below is exactly which domains, policies and data the agents are allowed to reason over.

In scope · the assessment itself

  • Six change types (triggers): new product · new feature · process change · vendor / third-party onboarding · new geography · new customer segment
  • Four risk domains (FFIEC BSA/AML Manual): customer or entity · product and service · geography · delivery channel and third party
  • Risk types inside those domains: money laundering · terrorist financing · sanctions exposure · third-party (vendor and agent) AML risk
  • Four outcomes: approve · approve with conditions · defer · reject
  • Jurisdiction: US-regulated bank; US federal supervisory framework; FATF lists for country risk

Out of scope · named so nobody asks

  • Fraud risk, credit risk, operational or market risk
  • Running sanctions screening or transaction monitoring (we assess whether those controls exist and how strong they are)
  • SAR / STR filing, case investigations, customer-level KYC decisions
  • Non-US regimes (EU AMLD, UK MLRs) beyond FATF country lists
  • Model-risk validation of the bank’s own ML models

Why this boundary

  • It is exactly the brief: "assess the financial crime risk a change introduces before it goes live"
  • FFIEC’s four domains are the published decomposition the brief demands
  • Small enough to seed a real policy corpus and a real control inventory in days
  • Wide enough that one demo case touches three of four domains

Reference data · what the assessment agent may rate

Control inventory · 24 controls

  • Geography: jurisdiction screening · corridor EDD · sanctions list screening (OFAC/UN/EU) · local licensing confirmation
  • Third party: vendor due diligence · payout-agent monitoring · contract AML clauses · agent KYC sampling
  • Product: transaction limits and velocity · product sign-off · monitoring rule coverage · disclosure and consent · fee transparency
  • Customer: KYC/CDD · EDD for high-risk · PEP screening · periodic refresh · beneficial ownership · adverse media · segment attestation
  • Each with weight, evidence artefact and test date

Scoring model v3

  • Likelihood and impact definitions 1–5 per domain
  • Retention floor 40%
  • Bands 1–4 · routing: 1–2 analyst, 3–4 committee
  • Boundary flag 0.5
  • Domain weights normalised across in-scope domains

Field set v6 · 18 required fields max

  • 6 always-required: change owner · description · go-live date · customer segment · volumes · partner / vendor identity (when a third party is involved)
  • Per-type extras: corridor countries · payout channels · licence numbers · data handled · process owner

03bHow the stack diagram maps to the services

The stack view (experience · harness cores · agents · tools · data) is the logical picture. The services are the deployment picture. One layer is not one service; here is the exact link and why.

Stack layerLives inReasoning
1 · Experiencefcrm-web + nginx + the SSE stream from case-serviceScreens are one deployable. Live updates come from the service that owns case state, so the UI never talks to agents directly
2 · Harness coresfcrm-orchestrator: four modules intake_core · assessment_core · decision_core · oversight_core, plus gate_manager. Evidence ledger and audit chain live in audit-service. Guardrails are a package used by orchestrator and agent workerThe harness is the orchestrator plus the guardrail and audit pieces it depends on; it is not "the services". Cores are stages of one case workflow, so they share one process and one state table. Ledger and chain are a separate service because they must be append-only and readable by the Examiner without going through workflow code
3 · Agent teamfcrm-agent-worker × N, loading the agent registryAgents are stateless workers behind a queue. Scale workers, not the orchestrator. One worker image runs any agent, so adding an agent is a folder, not a deployment
4 · Toolsfcrm_tools package; each tool is a thin read-only client to policy · scoring · case · audit servicesTools are the only way agents touch data. Backing them with service APIs means the same visibility and audit rules apply to agents as to people
5 · Governed dataMongoDB, one database per service; S3 Vectors indexes owned by policy-service; MinIO for filesOne database engine, many databases: documents match our versioned, nested records; boundaries stay clear. No cross-database reads; services call each other’s APIs
Guardrails railfcrm_guardrails package + OPA sidecarA package so every caller runs the same seven guards; OPA so permit decisions are declarative and testable outside Python
Trust railEvidence ledger (audit-service) · /evals + eval runner · OTel → LogfireThree different lifecycles: ledger is runtime data, evals are development-time, traces are operations. Kept separate so each can change alone

Why services at all, and why these five

Why split

  • Hackathon asks for production readiness and clear human/AI boundaries; a service boundary is the clearest boundary there is
  • Audit must be append-only and independently verifiable: own service, own database, no update path
  • Scoring must be pure and testable in isolation: own service, no database inside the function

Why not more

  • Agents are not services; they are jobs. One worker image, many agent folders
  • Guardrails are not a service; a network hop before every tool call adds latency and a failure point. A package plus OPA is enough
  • Nine days: each extra service is a template fork, env block and compose entry

Why not fewer

  • Merging audit into case-service would let workflow code update records. The chain must be out of reach
  • Merging scoring into case-service blurs "AI proposes, code computes", the single most-probed point
  • Decision (votes) has its own visibility rule (hidden until all cast); isolating it keeps that rule in one place

  • Prompt library fcrm_prompts/ · Markdown with front-matter (id, version, model tier, variables, eval set) · rendered with Jinja · version pinned on every proposal

04bMemory · what the system remembers, where, and why

Four kinds of memory. Three already exist in the design as durable MongoDB records. Redis is a cache, not a memory. Agent-memory products (Mem0 and similar) are kept out of the decision path.

KindHoldsLives inWhy there, and what it must never be
Working memory
one agent call		Only the fields, clauses, precedents and rules that agent needs for this step; the prompt plus tool resultsJob payload built by H1; token budget per tier (Guard 3); discarded after the callSmall, explicit context beats a long chat history. Never a rolling conversation: every call is reconstructable from its payload
Short-term memory
one case run		Every step, proposal, guard result, gate decision, retry, version in forcefcrm_harness.case_runs (event store) + fcrm_audit.proposalsIt is the audit trail, so it must be durable, ordered and versioned. Not Redis, not in-process state. Survives restarts; replays a case
Long-term memory
across cases		Closed cases with ratings and outcomes (precedents), override history, policy corpus versions, control evidence, jurisdiction listsfcrm_policy.precedent_index + S3 Vectors · fcrm_audit · fcrm_policyThis is the institutional memory the brief says the bank lacks ("depends on what the analyst remembers"). Queried by precedent_search, the critic and the examiner. Versioned so it never changes a past decision
Learning memory
how agents improve		What analysts keep overriding, eval scores per prompt versionOverride rate from fcrm_audit → eval rows in X6 → new P4 prompt versionLearning goes through a test and a versioned prompt, never an implicit store that silently changes behaviour. A regulator can see exactly when and why an agent changed

Redis · a cache and a bus, not a memory

Use it for

  • Token-validation cache in front of X1 (60 s TTL)
  • OPA decision cache for route and tool permits (short TTL, keyed by role · route or agent · tool)
  • SSE fan-out: pub/sub so any S1 replica can push a case event to the browser connected to another replica
  • Rate limits and idempotency keys for tool calls and uploads
  • Model-response cache for eval re-runs and demo rehearsals (Pydantic AI cached model wrapper; off in the production path)

Never for

  • Case state, proposals, gates or audit records
  • Anything the examiner might need to read back
  • Agent "memory" between cases

Required?

  • MVP: optional. One replica of each service; Mongo covers everything. The AEO identity clone already brings Redis, so it is present at zero cost
  • From two replicas of S1: required for SSE fan-out
  • Component ID X7 Redis, platform layer

Agent-memory products (Mem0, Zep, Letta and similar)

Why not in the decision path

  • They learn facts across sessions into a store the agent reads implicitly. That breaks no source, no claim: a proposal would rest on something with no document, version or record behind it
  • Nothing is retroactive here. An implicit memory changes behaviour without a prompt version, an eval run or a record, so two identical cases a week apart could be assessed differently with no visible reason
  • Our long-term memory is already explicit and queryable: precedents, overrides, corpus versions. The critic uses it with citations

Where one could help later

  • Analyst working preferences for the UI (which tab first, how questions are phrased), never as an input to proposals
  • Session summaries for the Examiner’s long conversations, as long as every answer still cites records
  • Decision: out of scope for this build; revisit only with an explicit "memory as a cited source" design

06Scoring · explained

The BA's engine, ported to its own service. Plain arithmetic. The AI proposes inputs; the engine computes; humans confirm inputs, never outputs.

Inputs (who sets them)

Likelihood 1–5Assessment agent proposes with written reason → analyst confirms or overrides
Impact 1–5Same. Informed by volume and customer exposure
Control effectiveness 0–10Per control, proposed from inventory + evidence date → analyst confirms. Stale evidence flagged. Planned controls excluded
Control weightFrom inventory. Sums to 1.00 per risk area. Config, not AI
Risk-area weightConfig. Normalised across areas in scope for the case

Chain

// per risk area in scope (of 4: customer · product · geography · channel/3rd party)
Inherent  = Likelihood × Impact                 // 1..25
CE        = weighted mean of control ratings
Retention = 1 − (0.6 × CE ÷ 10)                 // 1.00 .. 0.40  (40% floor)
Residual  = Inherent × Retention

// across areas
Composite = Σ Residual × normalised area weight
Band      = lookup(Composite)   // 1: 0–5 · 2: 5.1–10 · 3: 10.1–17 · 4: 17.1–25
Route     = bands 1–2 analyst closes · bands 3–4 committee

Worked example (the demo case)

Channel/3rd party  L4 I5 → 20 · CE 7.6 → ret 0.54 → 10.9 · w 0.45
Geography          L4 I4 → 16 · CE 6.0 → ret 0.64 → 10.2 · w 0.30
Product            L3 I4 → 12 · CE 6.5 → ret 0.61 →  7.3 · w 0.25
Composite = 4.91 + 3.06 + 1.83 = 9.8 → Band 2  (0.3 from Band 3: boundary flag)

Analyst overrides vendor DD 7.6 → 4.5 (stale, domestic-only audit)
Channel CE 7.6 → 4.5 · ret 0.73 · residual 14.6
Composite = 6.57 + 3.06 + 1.83 = 11.5 → Band 3 → committee

Design rules in the service

  • Pure and idempotent. Same inputs, same output. No database read inside the function
  • Versioned. Floor, band edges, weights live in a ScoringModelVersion document. A case pins the version it ran under. Changing config affects new cases only; re-score needs a reason and writes a record
  • Boundary flag. Within 0.5 of a band edge → analyst must acknowledge. Measured to the start of the neighbouring band
  • Rounding. Composite rounded to one decimal before band lookup, so nothing falls between 10.0 and 10.1
  • Tests. Worked example as fixtures · every band edge · floor at CE=10 · planned control ignored · property test: more control never raises residual
  • Full phase. Model-governance record per version (owner, approval, validation date), in the spirit of SR 26-2

07Data · MongoDB, FARM stack

One engine, one database per service, no cross-database reads. MongoDB because our records are versioned nested documents and the AEO templates already speak it. Vectors live in S3 Vectors, as the cloned context engine already does.

Databases (one per service)

  • fcrm_case · cases · submission_versions · field_values · documents · clarification_threads · conditions
  • fcrm_scoring · scoring_model_versions · routing_rules
  • fcrm_policy · corpus_versions · clauses (text + embedding) · controls · jurisdiction_list_versions · field_set_versions · precedent_index
  • fcrm_audit · proposals (evidence ledger) · audit_records (seq per case, prev_hash) · insert-only database user, no update/delete privilege · schema validation on the collection
  • fcrm_decision · packs · votes · outcomes
  • fcrm_harness · case_runs (event-sourced) · agent_jobs (atomic claims, as in AEO) · gates · budgets · outbox

Vectors and files

  • S3 Vectors (AWS) · three indexes: clauses · precedent_cases · controls · written by H4 through the cloned evoq_context backend, queried by S3
  • Metadata filters: corpus_version · jurisdiction · trigger_type · risk_area · closed_date · text match via Mongo text index, rank fusion in S3
  • Embeddings: Bedrock Titan v2 via evoq_context’s existing client; in-memory store for tests
  • Object store · MinIO (S3-compatible) locally · uploads, canonical Markdown, generated packs · AWS S3 later by config

Synthetic data and versions

  • Seed the BA’s 80 cases + 2 hand-written twins with the template’s masterdata loader on startup
  • Policy corpus: FFIEC sections + 3 internal standards as Markdown via evoq_ingestion, chunked by clause
  • FATF list June 2026 as jurisdiction_list v2026-06; v2026-10 fixture for the re-flag demo
  • Every reference collection versioned; a case stores {scoring_v, corpus_v, controls_v, fieldset_v, prompts_v}
  • Audit never deleted; files follow case retention; nightly mongodump
Why MongoDB: FARM is the team standard; the GenericService repository and job-worker claim pattern are reused unchanged; versioned nested records (submission versions, proposals with evidence) are documents; vectors live in S3 Vectors next to the files. Append-only on the audit database is enforced with an insert-only user plus collection schema validation.

08Evals · how we know it is good

Per-agent eval sets · /evals/<agent>/

  • intake · 80 cases × fields → extraction accuracy, category F1, gap-question precision
  • research · clause relevance (labelled), citation faithfulness (quote exists in source), gap honesty (no clause → says so)
  • assessment · L/I within ±1 of labelled, control match recall, stale-evidence detection
  • critic · planted-error set: unsourced claim, inflated rating, rule breach → detection rate
  • narrative · LLM-as-judge (DeepEval adapter from evoq_evals): grounded, no restricted terms in PO summary, conditions map to weak controls
  • examiner · every sentence cites a record; refusal when log lacks the answer
  • guardrails · red-team injection set, PII set, rule tests

Runner, gate, feedback

  • Runner: pydantic-evals + pytest, DeepEval/Ragas via the evoq_evals adapters · make evals
  • Results committed as JSON + HTML report per run · trend file
  • Gate: a prompt or model-tier change must pass its agent's set at or above the last score (pre-commit hook + make check)
  • Live signal: analyst override rate per agent (from audit) feeds a weekly review; large shifts open a prompt fix
  • Human sampling: 5% of closed cases re-read by a second analyst; disagreements become eval rows
  • Drift report: weekly rerun of all sets, diff against last

11Decisions to confirm

Model access · decided

Direct vendor keys through Pydantic AI providers. No LiteLLM proxy, no OpenRouter: Pydantic AI already gives one interface, fallback and usage. LiteLLM survives only as the SDK inside the cloned evoq_context for embeddings.

Five HTTP services or three

Five is the clean boundary set (case · scoring · policy · audit · decision). Three (case+decision, scoring+policy, audit) saves two forks. Recommend five; see 3b for why fewer blurs the lines the panel will probe.

Vector store · decided

S3 Vectors, as already built in evoq_context. Needs AWS credentials from day one; the in-memory store covers tests. MinIO still holds files locally.

OPA for tool permits

Extending the sidecar to agent→tool decisions is the strongest governance story (one policy engine for people and agents). Fallback: a Python allow-list in the tool registry. Recommend OPA.

Config screens

In scope per your decision. They are the three heaviest BA screens (Categories, Classification, Control inventory). Build them last; seed files cover the demo if time runs out.

Semgrep without CI

GitHub Actions and Trivy are out. Semgrep runs locally in make check and pre-commit so SAST evidence still exists in the repo (mentors named it).
