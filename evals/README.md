# evals

Per-agent evaluation for TrustOps' nine agents: datasets, metrics, a runner, the promotion gate, and a Markdown report. The design is in `docs/architecture/design/B-ai-layer.md` §7; this file says what exists today, what it measures, and what is still seeded.

## Layout

| Path | Holds |
|---|---|
| `src/packages/evals/` (`fcrm-evals`, import `fcrm_evals`) | All the code: generators, metrics, runner, gate, report, CLI. It is a uv workspace member like every other package. |
| `src/packages/evals/fcrm_evals/datasets/data/<agent>.jsonl` | The nine datasets. They are package data, generated by code and committed, the same way `fcrm_seed` bundles `seed.json`. |
| `evals/results/<run>/` (here) | Run output: `<agent>.<producer>.json`, `gate.json` and `report.md`. |
| `tests/unit/packages/evals/` | The unit tests, mirroring `src/` (ADR-21). |

**How this departs from `docs/architecture/folder-structure.md`.** That document puts `datasets/`, `metrics/`, `runners/` and `judge/` directly under `evals/`. Doing that would mean Python source outside `src/` with no `pyproject.toml`, which `ai/guidance/coding-standards.md` rules out ("Keep source code in the `src/` directory"; ADR-21). So the code lives in `src/packages/evals`, the datasets travel with the package that reads them (as `seed.json` does), and `evals/` keeps the brief's top-level folder for results and documentation. The rubric reads `evals/`, so this README points from there to the code.

## Commands

Run these from the repo root:

```bash
uv run --project src --package fcrm-evals python -m fcrm_evals build --check   # datasets == fresh build from the seed
uv run --project src --package fcrm-evals python -m fcrm_evals build           # regenerate datasets
uv run --project src --package fcrm-evals python -m fcrm_evals selfcheck --out evals/results/<run> [--timestamp ISO]
uv run --project src --package fcrm-evals python -m fcrm_evals run --producer echo|degraded|recorded [--agent A] [--outputs F.jsonl] --out evals/results/<run>
uv run --project src --package fcrm-evals pytest tests/unit/packages/evals
```

`make evals` should call `run`, and `make gate` should call `build --check` and `selfcheck`. The Makefile belongs to the ops lane, so that wiring is not done here.

## What is measured today, and what is not

**Measured, with real code and real numbers:**

- the datasets, which are derived from the seed and reproduce byte for byte;
- 27 metric definitions over the real `fcrm_contracts.proposals` schemas;
- the runner, the gate, and the report.

`evals/results/2026-10-04-selfcheck/` is a committed run. In that run:

- `echo` scores each dataset's own reference outputs. It reaches 1.000 on every metric for all nine agents, and it passes the gate over a degraded baseline. Anything below 1.000 would be a bug, and the first run did find one (see Findings).
- `degraded` scores the same outputs after deliberate, deterministic mistakes have been introduced. It fails the gate for all nine agents (table below).

**Not measured yet: any real agent.** `echo` and `degraded` exercise the measuring machinery. They are not agent baselines. The per-agent weekly figures in `seed.json["evals"]` (week 2026-09-28: intake 96.4%, research 99.1%, screening 96.2% and so on) are still the generator's **seeded targets**, not measurements. This matches the existing framing:

- `fcrm_seed/gen_seed.py` re-emits the walkthrough extraction and defers real synthesis.
- BUILD-PLAN §9 says "the seed's figures are labelled as the generator's targets".
- Design B §7.6 says "measured, not seeded".

They get replaced when a live or recorded run is committed. The seam for that is `CallableProducer` (or `RecordedProducer` with a `.jsonl` of outputs), driven by the real `fcrm_agents` runtime once that lane lands.

## Datasets (real sizes)

| Dataset | Rows | Where the expected values come from |
|---|---|---|
| `screening/fast-lane-100` | 100 | 80 seed cases plus 20 synthetic volume variants (10 feature-only cases at $4.2M and at $5.0M). Each label is produced by the **real** `fcrm_caseflow.routing.is_fast_lane_candidate`. Volume is recorded only for the demo ($48M); for the others it is "not recorded" and passed as `inf`. |
| `intake/extraction-80` | 80 | The demo has its 9 extracted field values with seed sources, 3 change types, and 3 answered gap questions. The page text is rendered by the generator. The 79 other cases carry change types only, because the seed has no field values for them. |
| `research/clauses-42` | 42 | The demo has its 4 accepted clauses (verbatim seed quotes) and precedent 0118 at 0.81. | `assessment/ratings-80` | 80 | All 80 cases, fully seed-real: L/I, matched controls, ratings and evidence dates from `case.inputs`. Staleness is computed by code. |
| `critic/planted-61` | 61 | The demo's 2 real findings (record #30 of the real 67-record chain), plus 20 closed cases × 3 planted errors. Their ledgers and 5-record chains are synthesized, and the chains are built with `fcrm_audit.chain.build_record`. |
| `narrative/recommendation-66` | 66 | The demo's real recommendation, conditions and facts. Its business summary text is synthesized. The 65 other closed cases use template text, which is synthesized. |
| `examiner/questions-5` | **5** | The seed's question and 7-sentence answer, 2 templated questions, and 2 unanswerable ones. Only the demo has a chain. Design B wants 120 rows, which needs H1's seed replay first. |
| `watchlist/reflag-29` | 29 | The fixture list diff, the current FATF diff, and 27 single-jurisdiction diffs. Labels are a set intersection over open cases. Only 2 seed cases have geographies at all. |

Each row's `rubric_notes` and `metadata.source` (`seed`/`demo`/`synthetic`) say exactly what was synthesized.

## Metrics, thresholds, and primaries

Thresholds come from design B §7.3 where it gives one. Otherwise they are marked *(proposed)*. All metrics are higher-is-better and micro-averaged (Σnum/Σden).

| Agent | Primary metric (gate) | Other metrics |
|---|---|---|
| screening | `fast_lane_precision` ≥ 0.90 | `fast_lane_recall` ≥ 0.90; `citation_validity` ≥ 0.95 |
| intake | `field_extraction_accuracy` ≥ 0.90 | `source_span_accuracy`, `category_f1` (micro-F1) and `gap_question_precision`, each ≥ 0.90; `citation_validity` |
| research | `clause_recall` ≥ 0.85 | `clause_precision` ≥ 0.70; `precedent_top1` ≥ 0.90 *(proposed)*; `citation_validity` |
| assessment | `li_within_one` ≥ 0.85 | `control_match_recall` ≥ 0.90; `control_match_precision` ≥ 0.90 and `evidence_date_exact` ≥ 0.95, both *(proposed)*; `citation_validity` |
| critic | `planted_error_detection` ≥ 0.85 | `critic_finding_groundedness` = 1.00 *(proposed)*; `citation_validity` |
| narrative | `number_grounding` = 1.00 | `narrative_restricted_terms` = 1.00; `conditions_traceable` = 1.00; `narrative_faithfulness` ≥ 0.90 (judge); `citation_validity` |
| examiner | `examiner_grounding` = 1.00 | `must_cite_coverage` ≥ 0.90 *(proposed)*; `refusal_rate` ≥ 0.95 |
| watchlist | `reflag_recall` = 1.00 | `reflag_precision` = 1.00 *(proposed)*; `citation_validity` |
| policy_gap | `gap_targets_recorded_gap` = 1.00 *(proposed)* | `suggestion_novelty` = 1.00 *(proposed)*; `citation_validity`. `suggestion_acceptance` is live-only and not computed. |

Several metrics reuse merged code instead of re-implementing it:

- `citation_validity` and `number_grounding` run Guard 4's own `verify_outputs`.
- `narrative_restricted_terms` uses rule 3's `restricted_terms_in`.
- `suggestion_novelty` uses `quote_match.match_quote`.
- Critic and examiner grounding resolve record refs against chains from `fcrm_audit.chain`. Each chain must pass `verify_chain` first, so a tampered chain grounds nothing.

**Judge.** `RubricJudgeMetric` k-votes over an *injected* async callable. `FakeJudge` is a deterministic heuristic stand-in: it uses no model and does not measure anything about a real judge. While the Bedrock judge is not wired, the narrative gate uses `number_grounding` rather than the design's judge metric. Wiring the Bedrock judge needs a judge prompt under `ai/prompts` and model ids in `ai/models/tiers.yaml`, and both belong to other lanes.

**Gate (design B §6.4).** A candidate passes only if all three hold:

- its primary metric is measured;
- that metric is ≥ its threshold;
- that metric is ≥ the baseline minus the tolerance (0 for deterministic metrics, 0.01 for judge metrics).

## Findings the datasets surfaced

1. **R4 code versus seed label.** `is_fast_lane_candidate` returns `true` for every `vendor_onboarding`-only case. The seed's own `fast_lane` flag is `true` only for FCRM-2026-0140 ("KYC vendor renewal"). Seven rows disagree (0088, 0091, 0110, 0123, 0129, 0133, 0139), including "Payout partner onboarding (Guatemala corridor)": an onboarding with a corridor is not a renewal. The dataset follows the code, as briefed, and records each disagreement in `metadata.label_conflict`. An agent that applies R4's "vendor renewal" wording correctly would lose recall on these rows.
2. **The seed flags stale evidence once; code finds 18.** The seed marks `stale: true` only on the demo's CTL-T01. Applying the 24-month rule to evidence dates finds 18 stale controls across the 80 cases.
3. **The first self-check failed, correctly.** Critic echo scored 0.984. The seed's second demo finding ("Only evidence is a 2023 audit of domestic operations…") identifies CTL-T01 by its evidence, not by name. The label was fixed, and the fix is documented in `critic.py`.
