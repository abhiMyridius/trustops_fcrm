# evals

Per-agent evaluation for TrustOps' nine agents: datasets, deterministic metrics, an LLM judge, a runner that calls the agents **live on Amazon Bedrock**, the promotion gate, a Markdown report and a one-page dashboard. The design is in `docs/architecture/design/B-ai-layer.md` §7; this file says what exists, how to run it, what a run measures and what the first real run found.

## Layout

| Path | Holds |
|---|---|
| `src/backend/packages/evals/` (`fcrm-evals`, import `fcrm_evals`) | All the code: generators, metrics, the live producer, the judge, runner, gate, reports, CLI. It is a uv workspace member like every other package. |
| `src/backend/packages/evals/fcrm_evals/datasets/data/<agent>.jsonl` | The nine datasets. They are package data, generated by code and committed, the same way `fcrm_seed` bundles `seed.json`. |
| `evals/results/<date>/` (here) | One run: `<agent>.live.json` (per-row scores, usage, the sample), `<agent>.outputs.jsonl` (what each agent produced), `gate.json` (nine verdicts), `index.json`, `report.md`, `dashboard.html`. |
| `evals/results/trend.jsonl`, `baseline.json`, `latest` | One line per run (the sparklines read it); the pointer to the run the gate compares with; a link to the newest run. |
| `evals/results/2026-10-04-selfcheck/` | The offline self-check (echo against degraded outputs). Not a measurement of an agent. |
| `tests/unit/packages/evals/`, `tests/integration/packages/evals/` | The unit tests and the live-MongoDB publish test, mirroring `src/` (ADR-21). |

**How this departs from `docs/architecture/folder-structure.md`.** That document puts `datasets/`, `metrics/`, `runners/` and `judge/` directly under `evals/`. Doing that would mean Python source outside `src/` with no `pyproject.toml`, which `ai/guidance/coding-standards.md` rules out ("Keep source code in the `src/` directory"; ADR-21). So the code lives in `src/backend/packages/evals`, the datasets travel with the package that reads them (as `seed.json` does), and `evals/` keeps the brief's top-level folder for results and documentation. The rubric reads `evals/`, so this README points from there to the code.

## Commands

Run these from the repo root. `make evals` needs the AWS credentials of the shell's environment (the standard chain) and calls Bedrock.

```bash
make evals                        # live, 5 rows per agent, seed 7, concurrency 3, Bedrock judge: about 10 minutes, USD 3-4
make evals AGENT=research         # one agent
make evals EVALS_ARGS="--baseline --publish"   # also make this run the baseline, and load it into Mongo
make evals EVALS_ARGS="--judge fake"           # no judge calls: the stand-in judge, labelled FAKE everywhere
make evals-full                   # every row of every dataset (slow, several times the cost)
make evals-gate AGENT=research    # the promotion gate on the newest run; exit 1 on FAIL

python -m fcrm_evals run --producer live --sample 5 --seed 7 --judge bedrock --judge-votes 3 --concurrency 3 [--row-ids a,b] [--baseline] [--publish --mongo-uri URI]
python -m fcrm_evals rerender [--results DIR]   # rebuild a run's verdicts, report and dashboard from its files: no model call
python -m fcrm_evals rejudge  [--results DIR]   # grade a run's saved outputs again: judge calls only, no agent is called
python -m fcrm_evals gate --agent A             # the same gate, without make

# offline, no AWS
python -m fcrm_evals build --check                       # datasets == fresh build from the seed
python -m fcrm_evals selfcheck --out evals/results/<run> # echo perfect and passing, degraded failing
python -m fcrm_evals run --producer echo|degraded|recorded [--agent A] [--outputs F.jsonl] --out DIR
uv run --project src/backend --all-packages pytest tests/unit/packages/evals
FCRM_TEST_MONGO_URI='mongodb://127.0.0.1:28217/?replicaSet=rs0' uv run --project src/backend --all-packages pytest -m integration tests/integration/packages/evals
```

`make gate` runs `build --check` and `selfcheck`; the live gate (`evals-gate`) needs a live run and is run on demand.

## How a live run works

For each agent, `python -m fcrm_evals run --producer live` does this, with no stand-in in the path:

1. **Sample.** `--sample N --seed S` draws N rows of the agent's dataset. The demo-case rows (FCRM-2026-0151) are always in. The rest are drawn by a seeded RNG, round-robin across the label a metric needs, because precision is undefined on a slice with no predicted positive: screening's 18 fast-lane rows in 100, watchlist's 3 re-flag rows in 29, examiner's unanswerable questions, the critic's three planted-error types. The same seed gives the same rows. `--row-ids` selects exact rows.
2. **Build the pack.** `RowPackBuilder` renders the row into a `ContextPack` under the real builders' section names, order, caps and line formats (`fcrm_agents.builders`). The row's own `sources` become the pack's sources, so a quote the agent copies from what it was shown verifies against Guard 4 and one it invents does not.
3. **Run the agent.** H2's `run_agent_live`: Guards 1 to 5, the seed-backed tools, a real `FallbackModel` on the agent's tier, the tier's token budget (cheap 6k, mid 12k, strong 20k tokens an attempt) and its one retry. Every request is metered (tokens, latency, the model that answered).
4. **Never fabricate.** A blocked run returns no items and a `blocked` flag with the guard that stopped it and Guard 4's feedback; a run that cannot build its pack or raises is `failed`. The metrics then score the empty output, which is what the agent produced. Failures are isolated per row and counted.
5. **Score.** The 27 deterministic metrics, plus, for narrative, examiner and critic, DeepEval's faithfulness, answer relevancy and hallucination metrics on the `judge` tier, and the real `narrative_faithfulness` judge (`--judge-votes K`).
6. **Gate.** One verdict per agent: the primary metric measured and at its threshold, no worse than the baseline's when there is one, **and at least 80% of the sampled rows completed**. The last rule is new and deliberate: a primary metric averaged over the one row that did produce an output reads as a pass for an agent that was refused on the other four (the first run's narrative gate did exactly that).
7. **Write.** The files under `evals/results/<date>/`, a line in `trend.jsonl`, the `latest` link, and with `--publish` the run in Mongo (`fcrm_evals.eval_runs`, `eval_dashboards`; shapes in `docs/architecture/data-model.md`).

`dashboard.html` is one self-contained page (inline CSS and SVG, no script, font or CDN): the run, the judge, the models, tokens and cost, "N/9 gates PASS", nine agent tiles, the gate chips, the guard strip and a collapsed per-metric table. It has no scrollbar at 1440 x 900 by construction (a fixed-height grid, `overflow: hidden`, no min-height but 0; a unit test asserts it), follows `prefers-color-scheme`, and says PASS or FAIL in words and icons as well as colour.

### Two switches that decide what a run measures

- **`--instructions raw|rendered`** (default `raw`). `raw` sends each agent its system prompt exactly as the H2 worker does today: the Jinja template unrendered, so `{{ config("routing.R4") }}`, `{{ skill("cite_verbatim") }}` and `{{ schema(...) }}` reach the model as text. `rendered` renders it fully (`fcrm_evals.instructions`), resolving the `routing.R4`, `corpus.catalogue` and `scoring.scales` excerpts from the seed and the `<Agent>Output` envelopes from the types Guard 4 enforces. The loader cannot do either today. The default measures the system as shipped; `rendered` measures it as designed.
- **`--token-budget-factor F`** (default 1.0). A **diagnostic**: scales the per-attempt token limits while the run lasts, to see an agent behind the budget that blocks it. A run that uses it says so on the dashboard, in `index.json` and in the report. A baseline is always 1.0.

### Cost and its caveat

Cost is an **estimate**: tokens from each Bedrock response times the list prices in `ai/models/tiers.yaml`, which that file marks `placeholder_confirm_before_go_live`. Reconcile against the AWS bill. Models are reported by the `label` `tiers.yaml` gives them (`Haiku 4.5`, `Opus 5.5`), never by id: result files live under `evals/` where ADR-04 forbids model ids, and every file a run writes passes through a redactor.

## The first live run (measured, not seeded)

`evals/results/2026-10-05/` is the baseline: `make evals` at `4c715bb`, 5 rows per agent, seed 7, Bedrock judge, the system as shipped (`raw` prompts, shipped budgets). **1 of 9 gates PASS.** The agents ran once, at `4c715bb`; the run's verdicts and judge grades were rebuilt at `8c5c9c8` from its saved outputs (`rerender` for the completion rule, `rejudge` for the corrected judge context), which is why `index.json` carries the earlier sha and the judge cost of 54 calls was paid twice (USD 1.2 each). The numbers below are the files' (`gate.json`, `index.json`); they replace the "seeded targets" the seed's `evals` block carried (intake 96.4%, research 99.1%, screening 96.2% ...), which the system as shipped does not meet.

|---|---|---|---|---|---|---|
| screening | fast_lane_precision | not measured | 0.90 | 0/5 | FAIL | token budget (5 rows: 6.7k to 7.1k tokens against 6k) |
| intake | field_extraction_accuracy | 0.000 | 0.90 | 0/5 | FAIL | token budget (8.2k to 11.1k against 6k) |
| research | clause_recall | 0.000 | 0.85 | 0/5 | FAIL | token budget (22k to 26k against 20k) |

| critic | planted_error_detection | 0.000 | 0.85 | 0/5 | FAIL | Guard 4 `records_resolve` on all 5 |
| narrative | number_grounding | 1.000 (1 row) | 1.00 | 1/5 | FAIL | completion 20%; Guard 4 on 4 rows |

The examiner is the one agent that ran to completion on every row, so its judge metrics are real: faithfulness 1.00, answer relevancy 1.00, hallucination-free 1.00 over 5 rows (`refusal_rate` 0.00 and `must_cite_coverage` 0.89 fail, see finding 6). The judge is the `judge` tier's Opus 5.5, a different model from every agent it grades except the critic's own tier.

### What stops the agents (evidence in `evals/results/2026-10-05/*.live.json`, one `run` record per row)

1. **The tier token budgets cannot hold a rendered or even a raw run.** Screening spends 6.7k to 7.1k tokens in two requests (the model calls one tool, the second request carries the whole prompt again) against a 6k budget; intake 8.2k to 11.1k; research 22k to 26k against 20k. The design priced a screening run at 1.8k (design B §2.1). A system prompt, the output tool's JSON schema and two tool definitions cost about 2.9k input tokens before the pack, which is 100 to 400 tokens. The runtime refuses the call after the second response (`usage limit exceeded`), so the row is blocked with a usable answer thrown away.
2. **Guard 4 fails closed on an empty answer.** Watchlist rows with no open case on the list diff (26 of 29) and policy_gap's demo row ended `no agent output to check; failing closed`: for the watchlist that is the *correct* answer ("no re-flag"), and H1 would open a handoff gate for it.
3. **An agent cannot cite what it is not given a handle for, and cannot cite what a tool returned.** With the budget lifted (below), screening still fails Guard 4: its reasons cite `doc:F02:p1` or `doc:case_metadata`, because nothing in the pack or the screening prompt (its only skill is `declare_gap`) says that a case field is cited as `{kind: case, case_id}`; the watchlist cites `list:jurisdiction_list@...` where the source is `list:fatf-fixture@...`, because no `list_id` is shown; research and policy_gap cite precedents and cases that a tool returned (`precedent_resolves failed (unresolved case:FCRM-2026-0122)`), but `LiveRun.post_guards` checks `pack.sources` only, not tool results, although design B §4 says H2 builds the sources from both.
4. **The critic's `record_refs` mixes in control ids.** All five critic rows end `records_resolve failed (uncited or unknown record)`; the debug trace of one row shows `record_refs: ['#4', 'ctl:CTL-G03']`. The model is right about the record and adds a reference the contract cannot hold.
5. **The retry starves a thinking model.** Attempt 2 runs the fallback alone with `max_tokens` halved (2,000 for the judge tier). Sonnet 5.5 and Opus 5.5 think adaptively and cannot switch it off (`tiers.yaml`), so a retried critic row spent the 2,000 tokens thinking and returned an empty tool call: `Exceeded maximum output retries (0)`. Four rows of the first run ended this way, and eight of the diagnostic run below.
6. **The examiner prompt and the `ExaminerAnswer` contract disagree.** `examiner.system.v1` tells the agent to set `answered`, `records_read` and a refusal reason; `ExaminerAnswer` has none of them, only `question` and `sentences`. Run unrendered, the agent refused the two unanswerable questions in a *sentence* ("Not answered: ..."); `refusal_rate`, defined as zero sentences, scores 0.00. Run rendered it returned zero sentences and scored 1.00.
7. **H2 sends the system prompt unrendered** (`fcrm_agent_worker.app._instructions_for` returns the raw body). With `rendered` the agents behave better (intake extracts 9 of 9 fields with 9 of 9 verified quotes, gap questions precise) but spend about three times the tokens, so finding 1 gets worse.

### The same run with the budget lifted and the prompts rendered (a diagnostic)

`evals/results/2026-10-05-diagnostic-rendered-x5/`: `--instructions rendered --token-budget-factor 5 --judge fake`, 5 rows per agent, about USD 4.26 and 1.4M tokens. **2 of 9 PASS** (intake: `field_extraction_accuracy` 1.00, source span 1.00, gap-question precision 1.00, citation validity 1.00 on the one completed row, and `category_f1` 0.00 because no category was proposed; examiner: grounding 1.00, `refusal_rate` 1.00, `must_cite_coverage` 0.89). The other seven are blocked by findings 2 to 5 above, which is the point of the diagnostic: with the budget out of the way the agents are stopped by their contracts and prompts, not by the model. This run uses the heuristic stand-in judge and says so; it is not a baseline.

## Datasets (real sizes)

| Dataset | Rows | Where the expected values come from |
|---|---|---|
| `screening/fast-lane-100` | 100 | 80 seed cases plus 20 synthetic volume variants (10 feature-only cases at $4.2M and at $5.0M). Each label is produced by the **real** `fcrm_caseflow.routing.is_fast_lane_candidate`. Volume is recorded only for the demo ($48M); for the others it is "not recorded" and passed as `inf`. |
| `intake/extraction-80` | 80 | The demo has its 9 extracted field values with seed sources, 3 change types, and 3 answered gap questions. The page text is rendered by the generator. The 79 other cases carry change types only, because the seed has no field values for them. |
| `research/clauses-42` | 42 | The demo has its 4 accepted clauses (verbatim seed quotes) and precedent 0118 at 0.81. | `assessment/ratings-80` | 80 | All 80 cases, fully seed-real: L/I, matched controls, ratings and evidence dates from `case.inputs`. Staleness is computed by code. |
| `critic/planted-61` | 61 | The demo's 2 real findings (record #30 of the real 67-record chain), plus 20 closed cases × 3 planted errors. Their ledgers and 5-record chains are synthesized, and the chains are built with `fcrm_audit.chain.build_record`. |
| `narrative/recommendation-66` | 66 | The demo's real recommendation, conditions and facts. Its business summary text is synthesized. The 65 other closed cases use template text, which is synthesized. |
| `examiner/questions-5` | **5** | The seed's question and 7-sentence answer, 2 templated questions, and 2 unanswerable ones. Only the demo has a chain. Design B wants 120 rows, which needs H1's seed replay first. |
| `watchlist/reflag-29` | 29 | The fixture list diff, the current FATF diff, and 27 single-jurisdiction diffs. Labels are a set intersection over open cases. Only 2 seed cases have geographies at all. |
| `policy_gap/suggestions-1` | **1** | The seed records one gap ("no clause for cash-pickup agent networks", record #45). The suggested clause text is synthesized. |

Each row's `rubric_notes` and `metadata.source` (`seed`/`demo`/`synthetic`) say exactly what was synthesized.

**What a row cannot carry, and how the pack handles it.** A row holds the facts it was generated from, not a case in the services. Where the real builder shows a section the row has no data for (screening's precedents, research's jurisdictions and controls, the narrative's findings) the section reads `(none)`, as the real builder's does for an empty list. Where the row has less than a field (a screening row has a title and a volume, not F01 to F06) the pack shows F02 and F05 in the real builder's `id · label · value · source` line and nothing invented.

## Metrics, thresholds, and primaries

Thresholds come from design B §7.3 where it gives one. Otherwise they are marked *(proposed)*. All metrics are higher-is-better and micro-averaged (Σnum/Σden); a judge metric's observation is its score over 1, so its aggregate is the mean score of the rows that were judged.

| Agent | Primary metric (gate) | Other metrics |
|---|---|---|
| screening | `fast_lane_precision` ≥ 0.90 | `fast_lane_recall` ≥ 0.90; `citation_validity` ≥ 0.95 |
| intake | `field_extraction_accuracy` ≥ 0.90 | `source_span_accuracy`, `category_f1` (micro-F1) and `gap_question_precision`, each ≥ 0.90; `citation_validity` |
| research | `clause_recall` ≥ 0.85 | `clause_precision` ≥ 0.70; `precedent_top1` ≥ 0.90 *(proposed)*; `citation_validity` |
| assessment | `li_within_one` ≥ 0.85 | `control_match_recall` ≥ 0.90; `control_match_precision` ≥ 0.90 and `evidence_date_exact` ≥ 0.95, both *(proposed)*; `citation_validity` |
| critic | `planted_error_detection` ≥ 0.85 | `critic_finding_groundedness` = 1.00 *(proposed)*; `citation_validity`; judge: `faithfulness`, `answer_relevancy`, `hallucination_free` |
| narrative | `number_grounding` = 1.00 | `narrative_restricted_terms` = 1.00; `conditions_traceable` = 1.00; `narrative_faithfulness` ≥ 0.90 (judge, k votes); `citation_validity`; judge: `faithfulness`, `answer_relevancy`, `hallucination_free` |
| examiner | `examiner_grounding` = 1.00 | `must_cite_coverage` ≥ 0.90 *(proposed)*; `refusal_rate` ≥ 0.95; judge: `faithfulness`, `answer_relevancy`, `hallucination_free` |
| watchlist | `reflag_recall` = 1.00 | `reflag_precision` = 1.00 *(proposed)*; `citation_validity` |
| policy_gap | `gap_targets_recorded_gap` = 1.00 *(proposed)* | `suggestion_novelty` = 1.00 *(proposed)*; `citation_validity`. `suggestion_acceptance` is live-only and not computed. |

The judge metrics are thresholds from the brief of this lane (*proposed*, not in design B): `faithfulness` ≥ 0.90, `answer_relevancy` ≥ 0.80, `hallucination_free` ≥ 0.90. They are **reported and shown on the dashboard, but they do not decide a gate**; the primary metric does.

Several metrics reuse merged code instead of re-implementing it:

- `citation_validity` and `number_grounding` run Guard 4's own `verify_outputs`.
- `narrative_restricted_terms` uses rule 3's `restricted_terms_in`.
- `suggestion_novelty` uses `quote_match.match_quote`.
- Critic and examiner grounding resolve record refs against chains from `fcrm_audit.chain`. Each chain must pass `verify_chain` first, so a tampered chain grounds nothing.

**The judge.** DeepEval 4.2.8's `FaithfulnessMetric`, `AnswerRelevancyMetric` and `HallucinationMetric` run on its `AmazonBedrockModel` (`BedrockJudgeLLM`) on the `judge` tier of `ai/models/tiers.yaml`: a model other than the assessor it grades (ADR-04). They read the pack the agent was shown (identity, versions and every fact line), not the dataset row. `hallucination_free` is DeepEval's hallucination score as it now reads (1 = no contradiction; the brief's "1 − score" for the older direction), checked ≥ 0.90. `narrative_faithfulness` keeps the design's rubric (every claim traceable 0.5, no invented number 0.3, emphasis on the real driver 0.2; pass ≥ 0.8; k votes) and takes its text from the prompt `narrative.judge` under `ai/prompts`. A row the judge cannot grade is *not measured*, counted and logged, never scored. `FakeJudge` (`--judge fake`) is a heuristic stand-in, not a model, and every output of such a run says FAKE.

**Gate (design B §6.4).** A candidate passes only if all hold: its primary metric is measured; it is ≥ its threshold; it is ≥ the baseline minus the tolerance (0 for deterministic metrics, 0.01 for a judge-graded primary); and, for a live run, at least 80% of the sampled rows completed. Sampled runs are only comparable with the same `--seed`.

## Self-check gate results (2026-10-04-selfcheck)

`evals/results/2026-10-04-selfcheck/` is a committed offline run. `echo` scores each dataset's own reference outputs and reaches 1.000 on every metric for all nine agents; `degraded` scores the same outputs after deterministic mistakes and fails the gate for all nine (screening 0.471, intake 0.778, research 0.656, assessment 0.412, critic 0.629, narrative 0.091, examiner 0.786, watchlist 0.250, policy_gap 0.000). Run the other way round, echo as the candidate over the degraded baseline, all nine PASS. Neither is an agent baseline; they prove the machinery measures something.

## Findings the datasets surfaced

1. **R4 code versus seed label.** `is_fast_lane_candidate` returns `true` for every `vendor_onboarding`-only case. The seed's own `fast_lane` flag is `true` only for FCRM-2026-0140 ("KYC vendor renewal"). Seven rows disagree (0088, 0091, 0110, 0123, 0129, 0133, 0139), including "Payout partner onboarding (Guatemala corridor)": an onboarding with a corridor is not a renewal. The dataset follows the code, as briefed, and records each disagreement in `metadata.label_conflict`. An agent that applies R4's "vendor renewal" wording correctly would lose recall on these rows.
2. **The seed flags stale evidence once; code finds 18.** The seed marks `stale: true` only on the demo's CTL-T01. Applying the 24-month rule to evidence dates finds 18 stale controls across the 80 cases.
3. **The first self-check failed, correctly.** Critic echo scored 0.984. The seed's second demo finding ("Only evidence is a 2023 audit of domestic operations…") identifies CTL-T01 by its evidence, not by name. The label was fixed, and the fix is documented in `critic.py`.
4. **`number_grounding` is strict about what counts as an input.** It checks numbers against the row's facts, so a narrative that repeats its own case id (`FCRM-2026-0090`) or a figure the agent read from the `case_record` tool (the demo's 62,000 monthly transactions) is flagged as ungrounded even though the tool returned it.
