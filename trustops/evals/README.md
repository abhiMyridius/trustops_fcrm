# evals

Per-agent evaluation for TrustOps' nine agents: datasets, deterministic metrics, an LLM judge, a runner that calls the agents **live on Amazon Bedrock**, the promotion gate, a Markdown report and a one-page dashboard. The design is in `docs/architecture/design/B-ai-layer.md` §7; this file says what exists, how to run it, what a run measures and what the first real run found.

**Note, 7 October 2026 (ADR-62, ADR-65): the committed model chain changed.** The committed chain is Sonnet 5.5 on the mid and strong tiers, Haiku 4.5 and Nova, with no Opus. Nova Pro replaced Opus 5.5 on the judge tier, and the strong tier's retry model is Sonnet 5.5, where it was Opus 5.5. ADR-62 first committed Sonnet 4.5 on mid and strong; ADR-65 replaced that choice the same day. Every measurement in this file was made on the 6 October chain, which ran Sonnet 5.5 on mid and strong and Opus 5.5 as the critic, the judge and the strong tier's first fallback: the committed baseline of 8 of 9 gates (run `7249d2a`), the cost of USD 3.14 a run, the demo case's token figures and the budgets' p90 columns. None has been repeated on the committed chain, so there is no committed eval baseline for it, and `baseline.json` still points at the run of the 6 October chain. A run of one row per agent on a Sonnet 4.5 chain (Nova Pro judge) gave 7 of 9 gates at about USD 0.44; it checked the runner, the Nova Pro judge and the dashboard, it is not a baseline, it describes a chain that is no longer committed, and its files are not committed. A `make evals` run on the committed chain is projected at about USD 1, because Nova Pro costs far less per token than Opus 5.5; that is not measured. The tables below are left as measured.

## Layout

| Path | Holds |
|---|---|
| `src/backend/packages/evals/` (`fcrm-evals`, import `fcrm_evals`) | All the code: generators, metrics, the live producer, the judge, runner, gate, reports, CLI. It is a uv workspace member like every other package. |
| `src/backend/packages/evals/fcrm_evals/datasets/data/<agent>.jsonl` | The nine datasets. They are package data, generated by code and committed, the same way `fcrm_seed` bundles `seed.json`. |
| `evals/results/<date>/` (here) | One run: `<agent>.live.json` (per-row scores, usage, the sample), `<agent>.outputs.jsonl` (what each agent produced), `gate.json` (nine verdicts), `index.json`, `report.md`, `dashboard.html`. |
| `evals/results/<date>-<what>/` | Other kept runs, same files: the diagnostic of 5 Oct, `2026-10-06-run1`, and the whole-dataset runs of one agent (below). |
| `evals/results/trend.jsonl`, `baseline.json`, `latest` | One line per run (the sparklines read it); the pointer to the run the gate compares with; a link to the newest run. |
| `evals/results/2026-10-04-selfcheck/` | The offline self-check (echo against degraded outputs). Not a measurement of an agent. |
| `tests/unit/packages/evals/`, `tests/integration/packages/evals/` | The unit tests and the live-MongoDB publish test, mirroring `src/` (ADR-21). |

**How this departs from `docs/architecture/folder-structure.md`.** That document puts `datasets/`, `metrics/`, `runners/` and `judge/` directly under `evals/`. Doing that would mean Python source outside `src/` with no `pyproject.toml`, which `ai/guidance/coding-standards.md` rules out ("Keep source code in the `src/` directory"; ADR-21). So the code lives in `src/backend/packages/evals`, the datasets travel with the package that reads them (as `seed.json` does), and `evals/` keeps the brief's top-level folder for results and documentation. The rubric reads `evals/`, so this README points from there to the code.

## Commands

Run these from the repo root. `make evals` needs the AWS credentials of the shell's environment (the standard chain) and calls Bedrock.

```bash
make evals                        # live, 5 rows per agent, seed 7, concurrency 3, Bedrock judge: about 7 minutes and USD 3.14 on the 6 October chain with an Opus 5.5 judge; projected at about USD 1 on the committed chain, not measured
make evals AGENT=research         # one agent
make evals EVALS_ARGS="--baseline --publish"   # also make this run the baseline, and load it into Mongo
make evals EVALS_ARGS="--judge fake"           # no judge calls: the stand-in judge, labelled FAKE everywhere
make evals EVALS_ARGS="--ai-root <a copy of ai/> --results-root <its own folder>"   # try another chain or prompt set without touching the shipped ai/; never a baseline
make evals-full                   # every row of every dataset (slow, several times the cost)
make evals-gate AGENT=research    # the promotion gate on the newest run; exit 1 on FAIL

python -m fcrm_evals run --producer live --sample 5 --seed 7 --judge bedrock --judge-votes 3 --concurrency 3 [--row-ids a,b] [--baseline] [--publish --mongo-uri URI]
python -m fcrm_evals rerender [--results DIR]   # rebuild a run's verdicts, report and dashboard from its files: no model call
python -m fcrm_evals rejudge  [--results DIR]   # grade a run's saved outputs again: judge calls only, no agent is called
python -m fcrm_evals gate --agent A             # the same gate, without make

# offline, no AWS
python -m fcrm_evals build --check                       # datasets == fresh build from the seed
python -m fcrm_evals selfcheck --out evals/results/<run> # echo perfect and passing, degraded failing
python -m fcrm_evals run --producer echo|degraded|recorded [--agent A] [--outputs F.jsonl] --out DIR
uv run --project src/backend --all-packages pytest tests/unit/packages/evals
FCRM_TEST_MONGO_URI='mongodb://127.0.0.1:28217/?replicaSet=rs0' uv run --project src/backend --all-packages pytest -m integration tests/integration/packages/evals
```

`make gate` runs `build --check` and `selfcheck`; the live gate (`evals-gate`) needs a live run and is run on demand.

`--ai-root` points a run at another `ai/` folder: its `tiers.yaml` and its prompts. It needs its own `--results-root`, and the CLI refuses `--baseline` and the shipped `evals/results` folder for any other root, so a result from a copy is never a baseline. The separate economy profile of 6 October (its own make targets, folder and model file) was removed on 7 October 2026 (ADR-62); the CLI keeps this flag.

## How a live run works

For each agent, `python -m fcrm_evals run --producer live` does this, with no stand-in in the path:

1. **Sample.** `--sample N --seed S` draws N rows of the agent's dataset. The demo-case rows (FCRM-2026-0151) are always in. The rest are drawn by a seeded RNG, round-robin across the label a metric needs, because precision is undefined on a slice with no predicted positive: screening's 18 fast-lane rows in 100, watchlist's 3 re-flag rows in 29, examiner's unanswerable questions, the critic's three planted-error types. The same seed gives the same rows. `--row-ids` selects exact rows.
2. **Build the pack.** `RowPackBuilder` renders the row into a `ContextPack` under the real builders' section names, order, caps and line formats (`fcrm_agents.builders`). The row's own `sources` become the pack's sources, widened the way production registers a case (`cite_case`: the field lines and the identity line the pack prints), so a quote the agent copies from what it was shown verifies against Guard 4 and one it invents does not. The `citation_validity` metric checks against the same list (`fcrm_evals.live.shown_sources`), never a narrower one.
3. **Run the agent.** H2's `run_agent_live`: Guards 1 to 5, the seed-backed tools, a real `FallbackModel` on the agent's tier, the system prompt rendered (`fcrm_prompts.InstructionRenderer`, the same renderer H2 uses), the tier's token budget (cheap 15k, mid 15k, strong 24k, judge 28k tokens an attempt; the judge was 20k until 7 October 2026; set from measured usage, below) and its one retry. Every request is metered (tokens, latency, the model that answered).
4. **Never fabricate.** A blocked run returns no items and a `blocked` flag with the guard that stopped it and Guard 4's feedback; a run that cannot build its pack or raises is `failed`. The metrics then score the empty output, which is what the agent produced. Failures are isolated per row and counted.
5. **Score.** The 27 deterministic metrics, plus, for narrative, examiner and critic, DeepEval's faithfulness, answer relevancy and hallucination metrics on the `judge` tier, and the real `narrative_faithfulness` judge (`--judge-votes K`).
6. **Gate.** One verdict per agent: the primary metric measured and at its threshold, no worse than the baseline's when there is one, **and at least 80% of the sampled rows completed**. The last rule is new and deliberate: a primary metric averaged over the one row that did produce an output reads as a pass for an agent that was refused on the other four (the first run's narrative gate did exactly that).
7. **Write.** The files under `evals/results/<date>/`, a line in `trend.jsonl`, the `latest` link, and with `--publish` the run in Mongo (`fcrm_evals.eval_runs`, `eval_dashboards`; shapes in `docs/architecture/data-model.md`).

`dashboard.html` is one self-contained page (inline CSS and SVG, no script, font or CDN): the run, the judge, the models, tokens and cost, "N/9 gates PASS", nine agent tiles, the gate chips, the guard strip and a collapsed per-metric table. It has no scrollbar at 1440 x 900 by construction (a fixed-height grid, `overflow: hidden`, no min-height but 0; a unit test asserts it), follows `prefers-color-scheme`, and says PASS or FAIL in words and icons as well as colour.

### Two switches that decide what a run measures

- **`--instructions rendered|raw`** (default `rendered`). `rendered` sends each agent its system prompt fully rendered by `fcrm_prompts.InstructionRenderer` (the `routing.R4`, `corpus.catalogue` and `scoring.scales` excerpts resolved from the seed, the skills expanded): that is what the H2 worker sends too, since the first live run found H2 sending the unrendered Jinja template (`{{ config("routing.R4") }}` reached the model as text). `raw` is kept as a diagnostic only, to reproduce that finding; a run that uses it says so on the dashboard.
- **`--token-budget-factor F`** (default 1.0). A **diagnostic**: scales the per-attempt token limits while the run lasts, to see an agent behind the budget that blocks it. A run that uses it says so on the dashboard, in `index.json` and in the report. A baseline is always 1.0.

### Cost and its caveat

Cost is an **estimate**: tokens from each Bedrock response times the list prices in `ai/models/tiers.yaml`. Those prices are **verified**: each row was read from the AWS Price List API on 6 Oct 2026 (us-east-1, the Regional rate card that the `us.` geographic cross-Region profiles bill at) and names its source. Every cost line says so: the dashboard header, the report note and `index.json` (`price_note`) print "verified AWS list prices, us-east-1, retrieved 2026-10-06" (the latest row date), or "unverified for: <models>" if a row is ever not verified. Reconcile against the AWS bill. The dollar figures in this README and in `ops/reports/token-analysis.md` are recomputed from each run's recorded tokens at the verified prices; the committed `index.json`, `report.md` and `dashboard.html` of the earlier runs were written at the earlier placeholder rates (`price_status` in their `index.json`), so they show lower figures (every Anthropic rate is exactly 1.10x its placeholder, so an Anthropic call costs 1.10x what its file records). The Opus 5.5 row left the price table on 7 October 2026 with the model; the figures here for runs that used it are those runs' recorded tokens at its verified rate (4.40 in and 22.00 out, USD per million tokens). The Sonnet 5.5 row (2.20 and 11.00) is in the table. The judge is Nova Pro now (0.80 and 3.20), so a run's judge share is not the 80% that `ops/reports/token-analysis.md` measured with Opus 5.5; no 5-row run has been made on the committed chain. Models are reported by the `label` `tiers.yaml` gives them (`Haiku 4.5`, `Nova Pro`), never by id: result files live under `evals/` where ADR-04 forbids model ids, and every file a run writes passes through a redactor.

### What stops the agents (evidence in `evals/results/2026-10-05/*.live.json`, one `run` record per row)

1. **The tier token budgets cannot hold a rendered or even a raw run.** Screening spends 6.7k to 7.1k tokens in two requests (the model calls one tool, the second request carries the whole prompt again) against a 6k budget; intake 8.2k to 11.1k; research 22k to 26k against 20k. The design priced a screening run at 1.8k (design B §2.1). A system prompt, the output tool's JSON schema and two tool definitions cost about 2.9k input tokens before the pack, which is 100 to 400 tokens. The runtime refuses the call after the second response (`usage limit exceeded`), so the row is blocked with a usable answer thrown away.
2. **Guard 4 fails closed on an empty answer.** Watchlist rows with no open case on the list diff (26 of 29) and policy_gap's demo row ended `no agent output to check; failing closed`: for the watchlist that is the *correct* answer ("no re-flag"), and H1 would open a handoff gate for it.
3. **An agent cannot cite what it is not given a handle for, and cannot cite what a tool returned.** With the budget lifted (below), screening still fails Guard 4: its reasons cite `doc:F02:p1` or `doc:case_metadata`, because nothing in the pack or the screening prompt (its only skill is `declare_gap`) says that a case field is cited as `{kind: case, case_id}`; the watchlist cites `list:jurisdiction_list@...` where the source is `list:fatf-fixture@...`, because no `list_id` is shown; research and policy_gap cite precedents and cases that a tool returned (`precedent_resolves failed (unresolved case:FCRM-2026-0122)`), but `LiveRun.post_guards` checks `pack.sources` only, not tool results, although design B §4 says H2 builds the sources from both.
4. **The critic's `record_refs` mixes in control ids.** All five critic rows end `records_resolve failed (uncited or unknown record)`; the debug trace of one row shows `record_refs: ['#4', 'ctl:CTL-G03']`. The model is right about the record and adds a reference the contract cannot hold.
5. **The retry starves a thinking model.** Attempt 2 runs the fallback alone with `max_tokens` halved (2,000 for the judge tier). Sonnet 5.5 and Opus 5.5 think adaptively and cannot switch it off (`tiers.yaml`), so a retried critic row spent the 2,000 tokens thinking and returned an empty tool call: `Exceeded maximum output retries (0)`. Four rows of the first run ended this way, and eight of the diagnostic run below.
6. **The examiner prompt and the `ExaminerAnswer` contract disagree.** `examiner.system.v1` tells the agent to set `answered`, `records_read` and a refusal reason; `ExaminerAnswer` has none of them, only `question` and `sentences`. Run unrendered, the agent refused the two unanswerable questions in a *sentence* ("Not answered: ..."); `refusal_rate`, defined as zero sentences, scores 0.00. Run rendered it returned zero sentences and scored 1.00.
7. **H2 sends the system prompt unrendered** (`fcrm_agent_worker.app._instructions_for` returns the raw body). With `rendered` the agents behave better (intake extracts 9 of 9 fields with 9 of 9 verified quotes, gap questions precise) but spend about three times the tokens, so finding 1 gets worse.

### Finding 5, before and after: a forced-style tool call and hidden reasoning

*Probed on Sonnet 5.5 and Opus 5.5 on 6 October 2026. Opus 5.5 has been in no chain since 7 October (ADR-62); Sonnet 5.5 is in the committed chain again (ADR-65), where mid and strong set `effort` low, which Sonnet 5.5 takes and Haiku and Nova reject. The probe was not repeated on the committed chain.*

A live probe through the runtime's own model wiring (`fcrm_agents.models`: the tier's primary model alone, `ToolOutput(list[Finding])`, one review task of four records, `retries=0`). Sonnet 5.5 and Opus 5.5 think adaptively and cannot switch it off; what changed is `output_config.effort`.

| Tier (model) | `max_tokens` | Effort | Output tokens | Reasoning block | Findings returned |
|---|---|---|---|---|---|
| mid (Sonnet 5.5) | 1,200 | default | 557 | no | 4 |
| mid (Sonnet 5.5) | 1,200 | low | 488 | no | 4 |
| mid (Sonnet 5.5) | 8,000 | default | 844 | yes | 5 |
| mid (Sonnet 5.5) | 8,000 | low | 560 | no | 4 |
| judge (Opus 5.5) | 1,200 | default | 920 | yes | 5 |
| judge (Opus 5.5) | 1,200 | low | 448 | no | 3 |
| judge (Opus 5.5) | 8,000 | default | 655 | yes | 4 |
| judge (Opus 5.5) | 8,000 | low | 489 | no | 3 |

At the default effort the judge tier spends up to 920 of 1,200 tokens before the answer; at low it spends 448 and emits no reasoning block. The probe's task is small, so it does not starve the call at 1,200 (the first run's critic rows did at 2,000 on a real pack, and a cut-off tool call arrives as `{}`); the measured effect is 12 to 51% fewer output tokens and no reasoning block. The retry also stops halving the allowance (`max_tokens_factor` is 1.0 on every attempt), and `max_tokens` is 4,000 / 4,000 / 8,000 / 8,000 (was 2,000 / 3,500 / 5,000 / 4,000). Haiku and Nova reject the field, so it is a per-model default (`effort_param` in `tiers.yaml`), never chain-wide. The judge metrics are thresholds from the brief of this lane (*proposed*, not in design B): `faithfulness` ≥ 0.90, `answer_relevancy` ≥ 0.80, `hallucination_free` ≥ 0.90. They are **reported and shown on the dashboard, but they do not decide a gate**; the primary metric does.

Several metrics reuse merged code instead of re-implementing it:

- `citation_validity` and `number_grounding` run Guard 4's own `verify_outputs`.
- `narrative_restricted_terms` uses rule 3's `restricted_terms_in`.
- `suggestion_novelty` uses `quote_match.match_quote`.
- Critic and examiner grounding resolve record refs against chains from `fcrm_audit.chain`. Each chain must pass `verify_chain` first, so a tampered chain grounds nothing.

**The judge.** DeepEval 4.2.8's `FaithfulnessMetric`, `AnswerRelevancyMetric` and `HallucinationMetric` run on its `AmazonBedrockModel` (`BedrockJudgeLLM`) on the `judge` tier of `ai/models/tiers.yaml`: a model other than the assessor it grades (ADR-04). On the committed chain that is Nova Pro, against Sonnet 5.5 on the assessor's side; the critic and the judge that grades its output are both Nova Pro, as both were Opus 5.5 on the 6 October chain. They read the pack the agent was shown (identity, versions and every fact line), not the dataset row. `hallucination_free` is DeepEval's hallucination score as it now reads (1 = no contradiction; the brief's "1 − score" for the older direction), checked ≥ 0.90. `narrative_faithfulness` keeps the design's rubric (every claim traceable 0.5, no invented number 0.3, emphasis on the real driver 0.2; pass ≥ 0.8; k votes) and takes its text from the prompt `narrative.judge` under `ai/prompts`. A row the judge cannot grade is *not measured*, counted and logged, never scored. `FakeJudge` (`--judge fake`) is a heuristic stand-in, not a model, and every output of such a run says FAKE.

**Gate (design B §6.4).** A candidate passes only if all hold: its primary metric is measured; it is ≥ its threshold; it is ≥ the baseline minus the tolerance (0 for deterministic metrics, 0.01 for a judge-graded primary); and, for a live run, at least 80% of the sampled rows completed. Sampled runs are only comparable with the same `--seed`.

## Findings the datasets surfaced

1. **R4 code versus seed label.** `is_fast_lane_candidate` returns `true` for every `vendor_onboarding`-only case. The seed's own `fast_lane` flag is `true` only for FCRM-2026-0140 ("KYC vendor renewal"). Seven rows disagree (0088, 0091, 0110, 0123, 0129, 0133, 0139), including "Payout partner onboarding (Guatemala corridor)": an onboarding with a corridor is not a renewal. The dataset follows the code, as briefed, and records each disagreement in `metadata.label_conflict`. An agent that applies R4's "vendor renewal" wording correctly would lose recall on these rows.
2. **The seed flags stale evidence once; code finds 18.** The seed marks `stale: true` only on the demo's CTL-T01. Applying the 24-month rule to evidence dates finds 18 stale controls across the 80 cases.
3. **The first self-check failed, correctly.** Critic echo scored 0.984. The seed's second demo finding ("Only evidence is a 2023 audit of domestic operations…") identifies CTL-T01 by its evidence, not by name. The label was fixed, and the fix is documented in `critic.py`.
4. **`number_grounding` is strict about what counts as an input.** It checks numbers against the row's facts, so a narrative that repeats its own case id (`FCRM-2026-0090`) or a figure the agent read from the `case_record` tool (the demo's 62,000 monthly transactions) is flagged as ungrounded even though the tool returned it.

5. **The assessment's L and I labels cannot be inferred from what a row carries.** A row holds a title, the domains in scope, the evidence list and the submission date; the labels come from the seed's per-domain factors. Over the 136 labelled domains of the 80 rows, L is spread evenly over 2 to 5 (34, 39, 30, 33) and I over 2 to 5 (41, 35, 32, 28); the same title and domain carries more than one (L, I) pair in 37 of 77 groups (a "Crypto custody pilot" customer factor is 3x2, 5x2, 5x4 and 5x5 on four rows). A constant guess of L 3, I 3 earns `li_within_one` 0.610 on those 136 domains, and the best constant guess per domain 0.676, so the 0.85 threshold sits above what any reading of the row can reach; the live agent scored 0.60 in the first 6 Oct run and 0.70 in the second on the same five rows (1.0, 0.5, 0.5, 1.0, 0.67 per row in the second), which is chance. This gate FAILS and is reported as failing: the fix is in the dataset (rows that carry the facts the factors were derived from), not in the agent, and the threshold was not touched.
6. **The 100-row screening run measures a different thing from the 5-row gate sample, and nothing applies R4's volume test.** The gate's five rows hold two fast-lane rows (both $4.2M variants); the full dataset holds 18. `fcrm_caseflow.routing.is_fast_lane_candidate` is called by no H1 path (only by this dataset's generator): the fast-lane gate opens on the screening agent's boolean as given, so design B §2.1's `fast_lane = code_criteria_met and agent.qualifies` is not implemented, while `screening.system` v2 told the model that code had applied the volume and change-type tests. On all 100 rows v2 scored precision 0.58 and recall 0.39: 5 false positives (feature-only changes at exactly $5M, which R4 excludes), 3 misses (feature-only at $4.2M, set false because the model answered "unknown" about a vendor renewal), and 8 misses on vendor onboardings, among them the one genuine renewal (0140, set false for the same reason). v3 scores 1.00 and 0.83. The three remaining misses (FCRM-2026-0088 Guatemala, 0110 Namibia, 0123 Colombia) are onboardings whose description names a new corridor or country; v3 lets that veto the fast lane, which the routing code does not (finding 1). `fast_lane_recall` 0.83 is below its 0.90 line and is left there.
7. **`precedent_top1` is 0.00 by construction.** A `PrecedentMatch` needs a `similarity` and an `outcome`; a research row carries the closed cases' text and the order of `precedent_candidates`, but neither number, so the eval pack cannot print them (production's pack prints `outcome · closed_date · score`) and the agent, correctly, proposes no precedent rather than invent them. Reading the outcomes from the seed's closed cases into the eval pack would make the metric measurable.
8. **The watchlist dataset and its pack disagree about removals.** Row `list:v2026-06` adds two countries and removes two (Algeria, Namibia); two open cases hold the removed ones, and the pack (like production's builder) lists both as candidates, but the label says no re-flag. The agent flagged one of them: `reflag_precision` is 0.80 over the 29 rows (one pair counted invented) with `reflag_recall` 1.00. Run on all 29 rows, USD 0.11.
9. **Intake's two-line briefs support no category.** Rows 0080 and 0109 hand the agent a two-line brief ("Case ...: Zelle limits increase / Business unit: Cards") and label two change types; the agent extracts no field, asks the required-field questions and proposes no `CategoryProposal`, so `category_f1` is 0.00 on those rows and 0.67 over the sample.
