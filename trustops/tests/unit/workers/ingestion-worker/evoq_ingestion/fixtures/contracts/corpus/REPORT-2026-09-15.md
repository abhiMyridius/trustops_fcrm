## 5. Real defects found and fixed during final integration

Exactly the kind of gap unit tests can't catch - a field-shape or invocation mismatch between two repos that each pass their own suite in isolation. All four were found running the corpus end to end for the first time with every prior lane's work in place; all four are fixed, lint/type-clean, and covered by a full green re-run of the affected repo's test suite after the fix.

1. **`aeocontextjob/evoq_context/chunking/tables.py::batch_rows` - O(max_rows squared) performance catastrophe.** For every batch, the inner loop re-rendered and re-tokenized the *entire accumulated batch text* once per row added (up to `CHUNK_MAX_ROWS=500` times per batch). Chunking the shared corpus's XLSX-04 scenario (200,001 rows) never completed - minutes of 100% CPU pinned inside `tiktoken`'s regex pretokenizer, with no end in sight. **Fixed** by binary-searching the batch boundary (same oracle function, O(log max_rows) calls instead of O(max_rows)) - behaviorally identical (all 519 `aeocontextjob` tests still pass unchanged) but now finishes XLSX-04 in ~31 seconds instead of hanging indefinitely.
2. **`aeocontextjob/evoq_context/cli.py::_cmd_chunk` didn't understand Canonical Document JSON**, despite its own docstring and `golden.py`'s calling convention documenting `chunk --json <canonical.json | file.md>` as supported input. It unconditionally did `path.read_text()` - feeding it a real canonical document JSON dump chunked the raw, JSON-escaped, no-real-newlines blob as one pathological "paragraph" (compounding defect #1's severity on XLSX-04, and silently corrupting chunking correctness for every other non-`chunk_only` scenario row in `golden.py`'s own harness). **Fixed**: `_cmd_chunk` now detects a canonical-document JSON input (has a `body_markdown` key) and extracts `body_markdown`/`file_name`/`profile_hints`, threading `profile_hints` through exactly like the real per-document pipeline (`utils/context_adapter.py` -> `vector/embedder.py`) does, falling back to raw-text chunking for anything else. Confirmed fixed by re-running the CLI directly on the real XLSX-04 canonical JSON (correct `table_aware` strategy, 2041 correctly-sized chunks, 31s).
3. **`golden.py`'s own `_chunks_of` helper mis-parsed the `chunk` CLI's real JSON shape.** It assumed separate top-level `"children"`/`"parents"` lists; the CLI actually emits one combined `"chunks"` list with a `"level"` discriminator per entry (plus `child_count`/`parent_count`). Every non-`chunk_only` context row was silently treating every parent as an extra child and always reporting **zero** parents - invisible until defect #2 above was fixed (before that, canonical-JSON rows were producing garbage output entirely, so this parsing bug was never actually exercised meaningfully). **Fixed**: `_chunks_of` now splits `payload["chunks"]` by its `"level"` field (with the `"children"`/`"parents"`-keys and `"records"`-list shapes kept as fallbacks for other callers/fixture shapes). Also added the missing `--source-type`/`--parent-child` flags to `golden.py`'s per-row `chunk` CLI invocation (Jira/Confluence rows need `source_type` for the selector's `source_type_in` rules - e.g. `comment_thread`; every row needs `--parent-child` to match the reconciled compose default `CHUNK_PARENT_CHILD_ENABLED=true`, since the standalone `chunk` CLI otherwise defaults it off for ad-hoc debugging).
4. **`aeocontextjob/evoq_context/chunking/parent_child.py::ParentChildSplitter` - the documented "single-child-equals-parent -> no parent" elision never fired for table segments.** It compared `ws_collapse(child.body)` (prefix stripped) to `ws_collapse(segment.text)`, but a table batch's `char_start`/`char_end` deliberately *excludes* the header/separator (which becomes `injected_prefix` instead, since it's re-rendered rather than a verbatim source slice - see `pipeline.py::_pack_table_segment`). That makes the two sides structurally unable to match for *any* single-batch table document, so every simple one-table XLSX/CSV document was silently getting a redundant, byte-identical parent chunk the code's own docstring says should never exist. Surfaced by CSV-03/CSV-04 failing their pinned `parents: [0, 0]` expectation once defect #3 stopped masking it. **Fixed**: the elision check now also accepts `ws_collapse(child.text)` (prefix *included*) matching the segment - catching the table case (re-rendered header/prefix is whitespace-equivalent to the segment's own) while an OR-only addition can't regress the original comparison. Confirmed via `aeocontextjob`'s full 519-test suite (unchanged) and a rebuild of this lane's own bundle (XLSX-02 dropped from 2 records - 1 child + 1 redundant parent - to the correct 1).

No other defects of this class were found; the remaining two golden-check failures (Section 6/7) are pre-existing scenario/threshold calibration edge cases on tiny synthetic fixtures, already flagged as `todo` notes by the scenario author in `golden.py`'s own report output - not integration defects.

## 8. Deviations from the plan

Compiled from what each lane actually reported/documented in code, not re-derived from scratch:

- **`extra="allow"` on both jobs' `Settings`, not `extra="ignore"`** as plan's reconciled cross-track decision #2 specifies. Functionally the compose-env-contract tests still catch the class of bug (`Settings(**compose_env)` construction) the decision was meant to guard; this is a naming/strictness deviation, not a coverage gap, but is called out here since it doesn't literally match the plan text.
- **`ParentChildSplitter`'s single-child-equals-parent elision required a second (`.text`-inclusive) comparison branch for table segments** - see Section 5 defect 4. Not a "kept legacy shim," but a genuine gap this lane closed; documented here since the original design (Section 2.1) described the elision as a single verbatim-text comparison.
- **`RowspanPolicy.repeat`** is the default rowspan-handling policy in `GfmRenderer` (rowspan -> repeat the cell value across the spanned rows), matching the plan's stated default; `blank`/`marker` remain selectable but are not exercised by the default corpus scenarios.
- **The two documented `OTLPSPAN_EXPORTER_ENDPOINT` gate deviations** (jobs gate on "non-empty," HTTP services gate on `'svc.cluster.local' in value`) are explicitly documented in both `apptracer/tracer_singleton.py` files and `config/config.py`'s inline comments - an intentional, disclosed deviation from the services' template, not new debt.
- **The `# JOB-DELTA:`-tagged-line diff-verification convention** (plan Section 3.1: "byte-identical to aeocontextservice's except # JOB-DELTA: marked lines") was not applied line-for-line in either job's `applogs/logger.py`/`apptracer/{tracer_singleton,metrics_singleton}.py` - the functional deltas described in the plan (root-logger binding, JobContextFilter, noisy-third-party quieting, ctx-suffix formatter, shutdown_app_logger/get_meter/shutdown_meter_provider convenience helpers, canonical OTLP_METRICS_EXPORTER_ENDPOINT naming) are all present and correct in both repos (verified by direct reading, Section 2's diff output, and the passing compose-env-contract tests), but a literal `diff <(sed 's/# JOB-DELTA.*//' ...) aeocontextservice/...` produces more than just the tagged deltas in all three files across both jobs (untagged reordering/additions, and in `aeocontextjob/applogs/logger.py`'s case the module's own docstring discusses the convention in prose that trips the naive sed pattern). This lane chose **not** to retrofit exact comment tags across six files this late in the process - the risk of a typo destabilizing working, tested logging/tracing glue for a purely cosmetic verification convenience outweighed the benefit. Documented here as an honest gap, not silently closed.
- **Two selector-threshold edge cases on tiny synthetic fixtures** (HTML-02, HTML-04 - Section 7/9) were already flagged by the scenario author as `todo` notes in `golden.py`'s own report output before this lane ran (e.g. "strategy assumes table_text_ratio >= 0.5 for this short page ... pin exactly once decided"), confirming these are pre-existing, anticipated calibration gaps rather than regressions introduced by this lane.
- **`AEO/contracts/fixtures/vectors_fixture.json`** (the committed, shared copy) is a pre-2.1 shape (20 vectors, no `parents` key) while both `evoq_context/cli.py fixture` (via `dump_fixture()`) and `golden.py export-vectors` are now capable of producing the full v2.1 `{vectors, parents}` shape - the MCP's own local test fixture already independently carries the v2.1 shape and passes its own suite, so nothing is actually blocked, but the shared `AEO/contracts/fixtures/vectors_fixture.json` itself was not regenerated/re-committed by this lane (regenerating a cross-repo contract fixture is explicitly framed by the CLI's own docstring as "for another repo to review and copy in," i.e. a deliberate, reviewed action - not something to do unreviewed inside a final-integration lane). See open risks.
