# Failure log

Append-only. How the build's own AI agents stalled, failed or made a mistake, how it was detected, and how it was recovered — the brief explicitly asks for this ("be ready to explain how the team's build agents stalled or failed, how you detected and recovered, and how your prompts evolved"). Every row here is a real incident from this build, not a hypothetical.

| # | When | What happened | How it was detected | Recovery | Lesson / prompt change |
|---|---|---|---|---|---|
| F-01 | 3 Oct, during wave-0 parallel dispatch | Five background subagents were launched in isolated git worktrees (`isolation: "worktree"`). A subsequent `git add -A` at the repo root swept up those worktree directories under `.claude/worktrees/` and committed them as embedded git repositories (gitlinks), which `git` warned about but did not block. | The `git add -A && git commit` command's own output showed five `warning: adding embedded git repository: ...` lines, which were read before moving on rather than ignored. | `git rm --cached -r` on each embedded path (left the files on disk, since the subagents were still using them), added `.claude/worktrees/` to `.gitignore`, and amended the commit before any further work landed on top of it. Verified afterward that every worktree was still checked out at a valid commit and in a clean state. | Always read `git status`/`git add` output for warnings, not just the exit code, before committing — especially right after dispatching anything that creates its own working directory. `.claude/worktrees/` is now ignored from the start of the repo's life. |
| F-02 | 3 Oct, same commit as F-01 | The commit's author/committer identity was corrupted: `git config --global user.name`/`user.email` held smart-quote-wrapped, truncated values (`"Abhishek <"abhishek.pahuja@myridius.com">`, name truncated to "Abhishek") instead of the straight-quoted values originally set, affecting all five commits made so far. | Routine post-commit `git log --format='%H %an <%ae>'` check (not triggered by an error — this is now a standing habit after any environment surprise). | Re-set `user.name`/`user.email` at both `--global` and `--local` scope with correct values; confirmed no remote existed (safe to rewrite); used `git filter-branch --env-filter` across `--all` to correct every commit's author and committer identity; expired the reflog and ran `git gc --prune=now` to drop the unreachable originals; confirmed every worktree (which share the same object store) remained checked out and functional afterward. | History rewrites are only safe when nothing has been pushed or shared — confirmed via `git remote -v` first. Check identity configuration early in a session rather than assuming it is intact, since something in the environment (not yet root-caused) can alter global git config between commands. |
| F-03 | 3 Oct, policy-service commit | A commit message passed inline via `git commit -m "..."` contained a backtick-wrapped word (`` `memory` ``) describing the `memory` VECTOR_BACKEND value. Backticks inside an unquoted-for-the-shell context triggered command substitution: the shell tried to run a command literally named `memory`, which doesn't exist, printed `command not found: memory` to stderr, and silently substituted empty output into the commit message — the word "memory" and its surrounding quote marks vanished from the stored message. | The shell's own `command not found: memory` line appeared in the tool output immediately after the commit, and was read rather than assumed to be unrelated noise; `git log -1 --format="%B"` was then run to inspect the actual stored message. | Wrote the intended message to a temp file with a heredoc (`cat > /tmp/commit-msg.txt <<'MSGEOF' ... MSGEOF`, quoted heredoc delimiter so nothing inside is shell-expanded) and `git commit --amend -F` that file, replacing the mangled message outright since it was still the unpushed tip commit. | Commit messages are now always written through a quoted heredoc to a temp file and passed with `-F`, never inline with `-m` containing backticks, `$(...)`, or unescaped `$variables` — removes an entire class of silent corruption rather than relying on remembering to escape each one. |
| F-04 | 3 Oct, merging the `fcrm_common` lane | A live-MongoDB verification step needed a disposable replica-set container. The host already runs a long-lived `mongo:8` container (port 27017) belonging to the operator's separate AEO platform. A new container started on a different port (27117) to avoid touching it got stuck in Docker's `Created` state and never actually started running, with no error and no logs — a known-bad interaction between this Docker Desktop installation and freshly created containers, independently hit by two different subagent lanes before this one. | `docker ps` showed the container absent from the running list; `docker ps -a` showed it wedged at `Created`; `docker start` was attempted and still produced nothing; `docker logs` returned empty. | Did not touch the operator's pre-existing `mongo:8` container at all. Removed the stuck disposable container (`docker rm -f`) and accepted the subagent's own already-verified result (236 of 243 tests passing without live Mongo; the 7 skipped tests are exactly the ones needing it) as the honest, correct state, rather than forcing a live run through a broken container runtime. | When a host's container runtime is already known (from another lane's report) to wedge on new containers, don't re-attempt the same live-infra verification expecting a different result — note the limitation once and move on with the already-good non-live result, and never redirect a verification step at infrastructure you don't own (the operator's running AEO containers) to work around it. |

| F-05 | 4 Oct, D-13's own fix | A fix I wrote myself (not a subagent) shipped with a real, subtler bug than the one it fixed: `fcrm_common.asgi.mount_at_root_path` wrapped a bare FastAPI app in an outer `Starlette(routes=[Mount(root_path, app=app)])` to make its routes answer at nginx's unstripped path prefix. Routing worked; the wrapped app's own `lifespan` (Mongo connection, signing-key load, readiness checks) silently never ran, because Starlette's `Router` does not cascade a `lifespan` ASGI scope into a `Mount`-ed sub-app. My own verification at the time (rebuild the scoring image, hit `/healthz`, check Docker's `HEALTHCHECK` says `healthy`) did not catch it, because the failure was vacuous, not loud: `/healthz` needs no lifespan state, and `/readyz` reported "ok" with zero checks registered rather than failing. | A *different* lane's (identity service) own routes hit lifespan-set state directly: `GET /.well-known/jwks.json` needs `app.state.signing_key`, set only inside `lifespan`. It 500'd with `AttributeError: 'State' object has no attribute 'signing_key'` when I ran that lane's Dockerfile against a real container — a route my own scoring-focused verification never exercised. | Rewrote `mount_at_root_path` as a thin functional ASGI wrapper that forwards the `lifespan` scope type untouched instead of nesting a second Starlette app around it (full detail in D-14), with a new regression test that asserts lifespan-set state is actually reachable through the mount, and re-verified both affected services end to end against real, separately-provisioned Mongo containers (not just `/healthz`). | A healthcheck or a route that needs no app-state can pass even when a deeper wiring bug (here, a skipped lifespan) is present — "the container reports healthy" is not proof that startup actually ran meaningfully. When verifying ASGI composition (mounting, middleware, wrapping), write a test that specifically asserts state set during startup is visible from inside a request, not only that routing resolves to the right handler. Also: a bug I introduce myself gets the same verify-before-trust treatment as a subagent's — don't exempt my own prior commit from scrutiny just because I wrote it carefully the first time. |
